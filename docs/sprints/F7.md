## Parte A — renovar sessão quando o backend devolve 403

### Diagnóstico
- `SecurityConfig` não configura `exceptionHandling`/entry point → Spring usa `Http403ForbiddenEntryPoint`. JWT ausente, inválido, **expirado** ou conta desativada (`JwtAuthenticationFilter` só não popula o contexto) → **403 sem corpo**.
- 403 "sem permissão" vem de `GlobalExceptionHandler` (ownership/`AccessDeniedException`, corpo JSON `error:"Forbidden"`), de `ResponseEntity.status(403).build()` (Dashboard/Investimento/Questionario/Admin) e de plano Premium (Chat usa 429/403 com `recurso`).
- Frontend: `tokenRefresh.deveTentarRefresh` só aceita **401** → o caso real (403) nunca renova; a request falha e o usuário fica preso até o `/auth/me` do próximo reload.
- Pontos de logout: interceptor em `api.js` (refresh falhou → limpa storage + `/login`), `AuthContext.logout` (UserMenu, ExclusaoContaModal), `/auth/me` no mount (só remove `authToken`).
- Fora do axios: `useExportacao.js` e download do `Chat.jsx` usam `fetch` cru — não passam pelo interceptor (fora de escopo, ver riscos).

### Regra adotada
Um 403 é **candidato a sessão expirada** quando, e somente quando:
1. existe `refreshToken` no `localStorage`;
2. a URL não é `/auth/login`, `/auth/refresh`, `/auth/registrar`;
3. a request ainda não foi reexecutada (`_retry` ausente).

Nesse caso o interceptor renova **uma vez** (single-flight já existente em `renovarSessao`) e reexecuta a request:
- reexecução OK → era sessão expirada; o chamador nem percebe;
- reexecução devolve 403 de novo → é **sem permissão**: `_retry=true` barra nova renovação, o erro sobe intacto ao chamador (Chat continua lendo `recurso`, etc.) e **não há logout**;
- renovação falha → logout (comportamento atual).

Não usamos o corpo da resposta como discriminador: tanto o entry point quanto os `.build()` devolvem 403 vazio, então corpo vazio não distingue os dois casos. O custo da regra é uma renovação extra em 403 de permissão real (raro, e rotação de refresh token é inócua).

### Anti-loop e concorrência
- Loop: `_retry` por request + URLs de auth excluídas + `renovarSessao` rejeita quando o próprio `/auth/refresh` falha.
- Concorrência: `refreshEmAndamento` (promessa única por módulo) — N requests que falham juntas aguardam a mesma renovação e reexecutam com o token novo. Já coberto por teste existente; acrescentar caso com 403.

### Entregas
- `src/services/tokenRefresh.js`: aceitar 401 **ou** 403 em `deveTentarRefresh`.
- `src/services/__tests__/tokenRefresh.test.js`: trocar a asserção `403 → false` por `describe('regressão: 403 do entry point do Spring')` cobrindo 403 candidato, 403 com `_retry`, 403 sem refresh token, 403 em URL de auth, e 403 persistente após renovação (sem logout). Vermelho antes, verde depois.
- `src/services/__tests__/api.interceptor.test.js` (novo, axios mockado com Vitest — sem MSW): 403 → refresh → retry OK; 403 → refresh → 403 de novo → erro propagado e `localStorage` intacto; 3 requests concorrentes → 1 `POST /auth/refresh`.
